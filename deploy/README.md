# Cross Charge — Deployment & Backfill Scripts

This folder contains PowerShell scripts for deploying the Cross Charge app across Dynatrace tenants and backfilling historical workflow executions.

---

## Prerequisites

### Files required at project root (one level up from this folder)

| File | Description |
|---|---|
| `secrets.json` | OAuth credentials and connection details (gitignored, never commit) |
| `tenants.csv` | List of target tenants |
| `out/artifact.zip` | Built app bundle — generated by `npm run deploy -- --dry-run` |

### `secrets.json` structure

```json
{
  "deployment": {
    "client_id":     "...",
    "client_secret": "...",
    "account_id":    "..."
  },
  "rate_card": {
    "client_id":     "...",
    "client_secret": "..."
  },
  "bizevent_target": {
    "name":  "GO-Prod",
    "url":   "https://tln90821.live.dynatrace.com",
    "token": "..."
  }
}
```

### `tenants.csv` structure

```csv
tenant_id,tenant_code,env,tag_key
wmw59814,GO,Dev,CrossChargeLicense
qve61453,GO,UAT,CrossChargeLicense
tln90821,GO,Prod,CrossChargeLicense
```

- `tenant_id` — Dynatrace environment ID (subdomain)
- `tenant_code` — short name for logging (e.g. GO, AH, BX)
- `env` — environment tier: `Dev`, `UAT`, or `Prod` — used for filtering
- `tag_key` — the tag key passed to the rate card settings for this tenant

### OAuth client scopes required

The OAuth client in `secrets.deployment` must have all of the following scopes:

| Scope | Used for |
|---|---|
| `app-engine:apps:install` | Installing the app bundle |
| `settings:objects:read` | Reading settings schemas |
| `settings:objects:write` | Creating bizevent and rate card settings |
| `automation:workflows:read` | Searching for and reading workflows |
| `automation:workflows:write` | Creating, updating, and deleting workflows |

### Build the app bundle

Before running either script, build the artifact:

```bash
npm run deploy -- --dry-run
```

This generates `out/artifact.zip` without deploying interactively.

## rollout.ps1 — Deploy to tenants

Deploys the Cross Charge app to every tenant in `tenants.csv`. For each tenant it runs six steps in sequence. If any critical step fails the tenant is skipped and the next one starts.

### What it does, step by step

```
[1] Get OAuth token       — client credentials flow against sso.dynatrace.com
[2] Delete old workflow   — searches for "Cross Charge Workflow" by title and deletes it
                            (non-fatal: warns and continues if not found or 403)
[3] Deploy app bundle     — POSTs artifact.zip to the App Engine registry
     └─ 30s wait          — gives the platform time to register the app's settings schemas
[4] Create bizevent settings
                          — POSTs to /api/v2/settings/objects on .live.dynatrace.com
                          — schema: app:my.cross.charge:send-bizevent-connection v0.0.1
                          — points all tenants to the central GO Prod bizevent ingest URL
                          — captures the returned objectId (used in step 6)
[5] Create rate card settings
                          — POSTs to /api/v2/settings/objects on .live.dynatrace.com
                          — schema: app:my.cross.charge:get-rate-card-connection v0.1.0
                          — tenant-specific: uses the tag_key from tenants.csv
                          — captures the returned objectId (used in step 6)
[6] Create workflow       — POSTs workflow-template.json to the Platform Automation API
                          — replaces BIZEVENT_CONNECTION_ID and RATE_CARD_CONNECTION_ID
                            placeholders with the objectIds from steps 4 and 5
                          — schedule: 5 PM daily, Australia/Sydney timezone
```

### API endpoints used

| Step | Method | Endpoint |
|---|---|---|
| Token | POST | `https://sso.dynatrace.com/sso/oauth2/token` |
| Search workflow | GET | `{tenant}.apps.dynatrace.com/platform/automation/v1/workflows?title=...` |
| Delete workflow | DELETE | `{tenant}.apps.dynatrace.com/platform/automation/v1/workflows/{id}` |
| Deploy app | POST | `{tenant}.apps.dynatrace.com/platform/app-engine/registry/v1/apps` |
| Create settings | POST | `{tenant}.live.dynatrace.com/api/v2/settings/objects` |
| Create workflow | POST | `{tenant}.apps.dynatrace.com/platform/automation/v1/workflows` |

### Usage

```powershell
# Deploy to all tenants
.\rollout.ps1

# Deploy only to a specific environment tier
.\rollout.ps1 -EnvFilter Prod
.\rollout.ps1 -EnvFilter UAT

# Deploy to a single tenant (for testing)
.\rollout.ps1 -TenantFilter wmw59814
```

### Output

- Console output with colour-coded status per step
- Timestamped log file saved to `deploy/rollout-YYYYMMDD-HHmmss.log`
- Summary table at the end showing OK / FAILED per tenant

### Notes

- Steps 4 and 5 create new settings objects every run — re-running on a tenant that was already deployed will create duplicate settings objects. Clean these up via the Settings API or Dynatrace UI before re-running.
- Step 2 (delete workflow) is non-fatal. A 403 on delete just logs a warning and continues.
- Estimated time: ~60–90 seconds per tenant (dominated by the 30s schema wait).

## backfill.ps1 — Trigger historical executions

Triggers the deployed workflow for every missing date across all tenants. Used to process historical data that was not captured by the daily schedule.

### How it works

The workflow's `get_date_range` action reads a `target_date` input field — if blank it defaults to yesterday, if set it processes that specific date. The backfill script exploits this by:

1. **Resolving workflow IDs** — queries the Automation API for "Cross Charge Workflow" on every tenant once at startup and caches the IDs
2. **For each date** in the range:
   - For each tenant: GETs the workflow JSON, replaces `target_date` via string substitution, PUTs the updated workflow back, then POSTs to `/runs` to trigger an execution
   - Waits `GapSeconds` (default 5 minutes) for executions to complete
   - Checks and logs the status of every execution triggered in that batch
3. **Restores** `target_date` to `""` on every tenant after all dates are done, so the daily schedule goes back to processing yesterday automatically

### API endpoints used

| Step | Method | Endpoint |
|---|---|---|
| Token | POST | `https://sso.dynatrace.com/sso/oauth2/token` |
| Find workflow | GET | `{tenant}.apps.dynatrace.com/platform/automation/v1/workflows?title=...` |
| Get workflow | GET | `{tenant}.apps.dynatrace.com/platform/automation/v1/workflows/{id}` |
| Update workflow | PUT | `{tenant}.apps.dynatrace.com/platform/automation/v1/workflows/{id}` |
| Trigger execution | POST | `{tenant}.apps.dynatrace.com/platform/automation/v1/workflows/{id}/runs` |
| Check execution | GET | `{tenant}.apps.dynatrace.com/platform/automation/v1/executions/{executionId}` |

### Usage

```powershell
# Full backfill with defaults (2026-09-07 to 2026-09-29, all tenants)
.\backfill.ps1

# Custom date range
.\backfill.ps1 -StartDate 2026-09-15 -EndDate 2026-09-29

# Single tenant (for testing)
.\backfill.ps1 -TenantFilter wmw59814 -StartDate 2026-09-07 -EndDate 2026-09-08

# Filter by environment
.\backfill.ps1 -EnvFilter Prod

# Shorter wait between date batches (workflows typically complete in ~3 min)
.\backfill.ps1 -GapSeconds 180
```

### Parameters

| Parameter | Default | Description |
|---|---|---|
| `-StartDate` | `2026-09-07` | First date to process (YYYY-MM-DD) |
| `-EndDate` | `2026-09-29` | Last date to process (YYYY-MM-DD) |
| `-EnvFilter` | _(all)_ | Filter tenants by `env` column |
| `-TenantFilter` | _(all)_ | Run against a single `tenant_id` |
| `-GapSeconds` | `300` | Seconds to wait between date batches |

### Timing

- 34 tenants × 23 dates = 782 executions total
- Each date batch takes ~90s to trigger all 34 tenants + `GapSeconds` wait
- Total estimated runtime with default 5-min gap: ~2 hours

### Output

- Console output showing trigger and status for every tenant and date
- Timestamped log file saved to `deploy/backfill-YYYYMMDD-HHmmss.log`
- Final summary: total SUCCESS / FAILED counts

### Status values

| Status | Meaning |
|---|---|
| `SUCCESS` | Workflow completed successfully |
| `RUNNING` | Still running after the gap — check manually |
| `FAILED` | Workflow failed — check execution logs in the tenant UI |
| `CANCELLED` | Execution was cancelled |

### Important notes

- A fresh OAuth token is fetched for every tenant operation to avoid expiry during long runs
- The `target_date` patch is done via JSON string replacement — no PSCustomObject property traversal — to handle the Platform API's response structure reliably
- If the script is interrupted mid-run, `target_date` may be left set on some workflows. Run the restore manually or re-run the script with a single-day range to trigger the restore at the end
- Executions still marked `RUNNING` at status-check time are counted as failures in the summary — this does not mean they will actually fail; increase `-GapSeconds` if workflows regularly take more than 5 minutes
